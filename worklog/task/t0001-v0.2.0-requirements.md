## Entity types supported in v0.2

| Name | Description | Notes |
|------|-------------|-------|
| Spec | Authoritative specification for a behavior. | |
| Task | One unit of work, completable in one session. | Archivable |
| Decision | Immutable record of rationale. | Optional. **Deprecated in v0.2.** |
| Reference (new) | External resources copied from a remote source. | Optional. Not numbered. Hierarchical management recommended. Original source's contents must be maintained: converting HTML to Markdown or extracting one section is permissible; rephrasing or adding clarification is not. |
| Note (new) | Non-authoritative guide/notes on working on a project. | Optional. Partially replaces Decision. |

## Issues observed in practice

- AI-generated specs and tasks are too verbose; hard for a human to read and review.
- An explicit way of tracking human review would be preferable.
- Decisions are made much more often than necessary.
- Agents spend too much time verifying worklogs, multiple times during a single task.
- At the same time, agents *still* do not archive completed tasks properly.
- Need a *constitutional* / *meta* spec governing *principles*: how other specs
  should behave.
- Hard to manage multiple related tasks.
- Priority alone is not enough to manage work track; agents don't use priority
  effectively.
- Some projects don't use worklog, or use something similar-but-different.
  Agents sometimes use worklog anyway — undesirable.
- Agents violate *work order*, especially for writing tasks.
- Current way of sectioning a worklog item seems inefficient and confusing.

Not directly worklog, but related:

- Worklog specs and code comments should contain *current state*, not *work
  history* unless necessary. This is a main cause of bloat.

## Notable changes for v0.2

- **Decisions deprecated.** New SKILL.md should briefly state that new decision
  items must not be created. Rationale: frequently misused, frequently created
  without human approval, frequently overturned later.
- **Hooks removed.** Harness either auto-approves or the user whitelists
  commands manually. Makes the skill compatible with more harnesses.
- **New tool set desirable** — more convenient tools reducing friction during work.

## Initial concerns for v0.2 items

- Scope of worklog Notes is too broad and vague.
- Decide whether specifying References is necessary at all.
- SKILL.md must stay concise; new entity types risk bloating it.
- *Minimize* the number of worklog item reads required per task.
- Need a mechanism to document and analyze frequent mistakes committed in a
  given project.
