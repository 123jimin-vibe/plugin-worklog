# The `tag` tool

Inspects and maintains the tag database defined by s0015.
s0005 governs shared diagnostics, disk I/O, and mutation guarantees; s0013 governs database initialization.

## Usage

```text
worklog tag list [--project PROJECT]
worklog tag add TAG [--description TEXT] [--project PROJECT]
worklog tag update TAG [--name NEW_TAG] [--description TEXT] [--project PROJECT]
worklog tag remove TAG [--project PROJECT]
```

Every action requires an existing valid tag database.
A missing or malformed database prevents the action without changing worklog files.
Names, uniqueness, CSV representation, and reference coverage follow s0015.

## Actions

- `list` reports every registered tag and description in normalized-name order.
  It identifies unknown entity tags and unused database rows as advisory information.
- `add` rejects an already registered normalized name.
  It stores the normalized name and uses an empty description when `--description` is omitted.
- `update` requires an existing tag and MUST receive `--name`, `--description`, or both.
  Omitted properties are preserved.
  A rename rejects an already registered destination and any resulting duplicate normalized tag within an affected entity.
  It updates the database and every matching current entity and archived task as one operation, and reports each changed entity and its applicable mode.
  Reference contents and decision rationale are not rewritten.
- `remove` rejects an unregistered or referenced tag.
  A referenced-tag rejection identifies every referring entity.

Mutations preflight the complete affected change before writing, using the shared guarantees in s0005.
An actual rename means that the normalized new name differs from the existing normalized name.

## Required inputs and results

- `add` and a description-only update need only the database and supplied arguments.
  An update whose `--name` normalizes to the existing name likewise requires no entity scan.
  These actions MUST NOT read entity files or project mode configuration.
- `list`, `remove`, and an actual rename require complete tag-usage coverage across current entities and archived tasks.
  Unrelated title, identity, hierarchy, or dependency defects MUST NOT prevent that coverage or produce diagnostics.
  Invalid tag values or unparseable metadata that prevents determining usage are relevant errors.
- A rename requires effective mode reporting only for entities whose tags it changes.
  Mode reporting does not establish the caller's edit permission or content approval.
- `list` MUST preserve useful database output if tag-usage coverage fails, identify the incomplete result, and fail according to s0005.
  It MUST NOT claim that a row is unused without the required coverage.
- Mutations requiring tag coverage MUST NOT publish changes when that coverage cannot be established.
  Other database rows' usage is not diagnostic output for a mutation unless it affects that action.
- Read-only results and byte-identical updates follow the no-write rules in s0005.
