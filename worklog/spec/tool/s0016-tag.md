# The `tag` tool

```text
worklog tag list [--project PROJECT]
worklog tag add TAG [--description TEXT] [--project PROJECT]
worklog tag update TAG [--name NEW_TAG] [--description TEXT] [--project PROJECT]
worklog tag remove TAG [--project PROJECT]
```

All actions require an existing valid database under s0015; otherwise they fail without changes.
Shared rules follow s0005; initialization belongs to s0013.

## Actions

- `list`: report registered tags and descriptions in normalized-name order, plus advisory unknown tags and unused rows.
- `add`: reject a registered name; otherwise store the normalized name with the supplied description or an empty one.
- `update` requires a registered tag and MUST receive `--name`, `--description`, or both; omitted properties are preserved.
  A normalized-name change rejects a registered destination or resulting duplicate tags, and updates the database and all matching current/archived entities as one operation.
  Report each changed entity and its applicable mode; preserve reference contents and decision rationale.
- `remove`: reject an unregistered or referenced tag, identifying all referring entities.

## Scope

- Adding a tag or updating without a normalized-name change needs only the database and arguments, and MUST NOT read entity files or mode configuration.
- Listing, removal, and renaming require complete tag-usage coverage across current entities and archived tasks.
  Validate tag values and metadata parseability, not unrelated fields.
  Unrelated metadata defects MUST NOT block coverage or produce diagnostics.
  Mutations require that coverage before publication; their usage diagnostics concern the selected tag.
- If usage discovery fails, `list` MUST retain useful database output, identify incomplete coverage, and return failure without claiming unused rows.
- Renames require mode reporting only for changed entities.
  Read-only results and byte-identical updates make no writes.
